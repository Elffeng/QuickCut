# 六人并行实施任务书

版本：规划稿 0.1。更新日期：2026-11-06。代码基线：`6cb978d`。

本文把已经确认的产品结构拆成六份相对独立的工作。它描述的是下一阶段的实现目标，不代表多素材、外部空镜库和剪映工程导出已经完成。当前代码能力见 [MVP 基线审计](mvp-baseline.md)，总体工作流见 [项目指导文件](../PROJECT_GUIDE.zh-CN.md)，数据约定见 [模块交付协议](contracts.md)。

## 1. 我们共同交付的是什么

用户先告诉系统想讲的故事、成片类型、语言、时长和风格，再上传一组长短不一的视频。系统需要从这些素材里找出有用的事件和视角，结合外部风景空镜安排环境交代、转场和留白。经过从素材级、事件级、镜头级到边界级的逐级收敛，生成故事完整、声音与画面对应的可编辑时间线，最后交付预览视频与剪映草稿工程。

工程交付必须保留可独立编辑的画面、空镜、原声、配音和字幕；如使用音乐，也保留其独立引用。主画面与空镜可以在同一画面轨道上使用不同 clip 和 role 表达，不强制空镜另占一条轨。预览 MP4 用于检查，不能替代可继续精修的工程。这里的“外部空镜”和“外部配音”表示它们不是用户原视频的一部分；模型推理和配音合成仍在本地执行。

六个人不按“各自做一个模型”分工，而按稳定的输入输出分工。任何人都应该能用手写样例运行自己的模块，不必等前一个人把模型完全做好。模型效果提升、媒体处理、工程导出因此可以同时推进。

## 2. 六个模块与边界

| 角色 | 一句话目标 | 主输入 | 主交付物 | 主要接收方 |
|---|---|---|---|---|
| A：素材接入与索引 | 把一组原视频变成可追溯、可检索的素材集合 | 用户视频、外部视频文件、处理配置 | `AssetManifest` 与代理视频、关键帧、ASR 文件 | B、D、F |
| B：检索与外部空镜库 | 根据叙事需求找到合适且可用的候选片段 | `AssetManifest`、`RetrievalRequest` | `CandidateSet` | C |
| C：故事与视听规划 | 让用户想讲的故事和真实素材能够对应 | `Brief`、`CandidateSet`、视觉证据 | `StoryPlan`、新的 `RetrievalRequest` | B、D、E |
| D：精剪与时间线编排 | 将故事板变成唯一、可执行的成片时间安排 | `StoryPlan`、`AssetManifest`、`VoicePackage` | `EditTimeline`、修订请求 | E、F、C |
| E：本地配音与字幕 | 将确定的台词变成可独立替换的声音和字幕 | 配音句子、句子预算或目标区间、声音配置 | `VoicePackage` | D、F |
| F：渲染与剪映交付 | 按时间线生成可播放预览和可继续编辑的工程 | `EditTimeline`、素材引用、`VoicePackage` | `ExportManifest`、工程包、预览和验证报告 | 全组、最终使用者 |

必须区分两个时间坐标：源时间回答“从哪份原视频的哪里取素材”，成片时间回答“这个片段何时出现在最终视频中”。新协议统一使用整数微秒与半开区间 `[begin, end)`；原代码中的秒浮点值通过兼容适配器转换，不可在同一字段内混用。

项目标识使用 `project_id`；素材、片段、故事段、配音句子和轨道分别使用 `asset_id`、`segment_id`、`beat_id`、`cue_id`、`track_id`。具体字段和必填约束以协议文件为准，不由各模块自行增加同义字段。

### 决策权

- A 维护素材事实：原始文件、时长、视频参数、源时间、关键帧和识别结果。
- B 维护检索结果：候选、分数、召回依据、过滤结果；B 不决定故事结局。
- C 维护叙事和事实表达：段落目的、镜头职责、关键事件、旁白文本、缺口处理。
- D 是成片时间线的唯一编排者：镜头与声音轨的最终位置、修剪、重排和版本更新。
- E 维护声音事实：实际合成音频、真实时长、音色、语速、字幕文本与句子对齐。
- F 按已经确定的时间线执行渲染和工程映射；F 不自行增删剧情、重排镜头或修改台词。

## 3. A：素材接入与索引

### 任务的意义

所有下游模块都必须知道素材真实存在，而且能够精确定位回原片。A 提供这一基础。对于多个短视频，A 既要保留每个文件的来源，又要提供可跨文件检索的统一片段集合；对于长视频，A 先做粗分段，不能把整个文件当成一个候选镜头。

### 范围与输入

输入是一组视频文件及其来源标记。A 负责媒体探测、文件身份与重复导入识别、代理视频、粗粒度场景或窗口划分、关键帧抽取、ASR、缓存、处理状态和失败重试。原片保持可追溯，代理视频不能覆盖原片。外部空镜文件也使用相同接入通道，但其库标签、语义索引和召回由 B 负责。

A 不负责故事顺序、最终出入点、CLIP 检索排名或对同一人物的长期身份作确定性判断。A 可以记录拍摄时间，但文件时间和镜头时间不能直接冒充跨设备的真实事件顺序。

### 可复用代码

- [core.py](../../quickcut/core.py)：`probe_video`、`extract_keyframe`、`build_index`、缓存和 PNG 完整性检查。
- [asr.py](../../quickcut/asr.py)：本地 faster-whisper 适配、transcript sidecar、时间区间挂接。
- [types.py](../../quickcut/types.py)：现有 `Shot`、`IndexManifest` 可作为迁移起点；目前不是完整多源协议。
- [test_core.py](../../tests/test_core.py)、[test_asr.py](../../tests/test_asr.py)：基础回归样例。

### P0：首个可联调版本

1. 接受文件列表，为每个文件分配稳定身份，并保留项目内来源引用。
2. 输出多素材 `AssetManifest`，区分文件、事件候选/粗段和镜头候选的层级；先允许固定窗口方案，明确标记分段方法。
3. 支持代理视频和关键帧；保存原片与代理时间对应关系，避免不同帧率导致取错片段。
4. 对有语音的素材运行本地 ASR；无音轨、无有效对白与 ASR 执行失败必须是不同状态。
5. 缓存绑定素材身份和处理配置，重复运行可复用；坏关键帧不能作为有效视觉证据交付。
6. 单个文件失败不应抹掉其他文件的成功结果，交付中标明可重试的失败项。

### P1：后续增强

加入场景切换候选、音频停顿边界、基础模糊/曝光/静帧指标、增量索引与中断恢复。更细的动作出入点交给 D，不要求 A 对全片执行高成本 VLM。

### 第一份独立交付

第一轮使用三段短视频、一段长视频和两段空镜构造样例。即使 ASR 或视觉模型尚未准备好，也先用可解码的媒体和明确的空 transcript 跑通文件到 Manifest 的链路；测试中使用 mock 时必须标记，不能写成真实推理结果。

交给 B 的是 Manifest、关键帧和 transcript；交给 D、F 的是素材引用、源时间、媒体参数和代理映射。每份交付带一个可运行入口及示例输出。

### 验收与反馈

- 任取一个片段，能打开正确原片并定位到对应源时间。
- 混合长短视频、无音轨视频、不同分辨率/帧率视频均有明确处理结果。
- 相同输入和配置重复执行，素材身份不变化；新增文件无需重建所有旧文件。
- 缺文件、解码失败、ASR 失败、关键帧损坏能够返回到具体 `asset_id` 或 `segment_id`。
- 不向 B 交付“有 embedding 但图片并不存在”的视觉候选。

## 4. B：检索与外部空镜库

### 任务的意义

B 将“我需要一个交代清晨环境的镜头”变成可供 C 比较的真实候选。它既处理用户拍到的主内容，也处理库中的空镜，但始终保留来源区别。空镜可以承担开场、转场和情绪留白，不应因为颜色相似就被当成用户真实经历的证据。

### 范围与输入

输入是 A 的 Manifest 和 C 的 `RetrievalRequest`。每次请求应说明所属段落、镜头职责、内容要求和硬约束。B 负责图文向量、transcript 检索、外部库元数据、语义去重和候选质量排序。输出候选与依据，不输出最终故事结构。

空镜库的初始导入可以来自一组本地文件。跨互联网采购、无限自动下载和自动授权判断不属于首轮实现要求。库资产应记录来源引用及已知使用信息，便于 F 打包时保留出处。

### 可复用代码

- [encoder.py](../../quickcut/encoder.py)：OpenCLIP/MobileCLIP 适配、归一化图文向量与余弦相似度。
- [core.py](../../quickcut/core.py)：`localize` 和 transcript 词面重合评分可作为基线。
- [test_encoder.py](../../tests/test_encoder.py)：现有编码测试。

当前 fallback 是颜色直方图与颜色词规则，不应作为 CLIP 语义检索的验收结果。现有中文 transcript 词面匹配也不能直接等同于中文语义检索。

### P0：首个可联调版本

1. 接收统一 Manifest，为用户素材和外部空镜建立可区分的检索视图。
2. 封装可替换视觉编码器，记录模型名称、权重来源、特征版本和维度。
3. 组合视觉召回、transcript 召回、来源过滤和时长/画幅约束；不要将不同尺度的分数当作已校准概率。
4. 输出 `CandidateSet`，含候选来源、相关性依据、质量标记和未满足条件。
5. 支持外部空镜的场景、情绪、光线和镜头运动等标签；机器预测标签保留其生成方式。
6. 空集合是合法结果。没有合适素材时明确返回缺口，不用无关片段填满数量。

### P1：后续增强

优化中文查询、近重复镜头聚类、多样性重排、镜头运动与色调匹配，并用带人工标注的查询集测量检索提升。检索请求可以按故事段落增量执行，不需要每次重算全部 embedding。

### 第一份独立交付

使用手写 Manifest 和本地小素材库，支持“用户主镜头”“环境空镜”“无匹配结果”三种查询。C 可以立即消费 CandidateSet，即使索引尚未来自 A 的自动流程。

### 验收与反馈

- 每个候选能够追溯到 A 的真实片段，不生成不存在的 ID。
- 来源过滤、时长/画幅等硬约束可重复验证。
- 同一个外部空镜不会因为重复导入挤占整个候选列表。
- 对事先标注的查询，报告召回结果和失败样例；首次协议会上确定统一的相关性评测集，不事后挑选成功示例。
- B 向 C 返回“找到什么、缺什么”；由 C 决定改写故事、换表达或发起下一次请求。

## 5. C：故事与视听规划

### 任务的意义

C 是用户意图与素材事实之间的协调者。它先根据 Brief 建立初始结构，再用真实候选核对这个结构是否可实现。它需要同时考虑主内容、空镜、旁白和原声，而不是把镜头选完后再拼上一段通用解说。

### 范围与输入

输入是 Brief、候选集、视觉证据及必要的 transcript。C 负责段落目的、关键事件、镜头职责、模型选镜与顺序、旁白脚本和段落预算；D 负责将这些安排落实到可执行的精细时间轴。

C 可以向 B 反复发起有明确目的的检索，但每次要记录缺口和调整原因，并设置有限的重试/规划次数。用户的故事愿望与素材可证实的事件应分别保存。外部空镜不负责证明用户素材中不存在的具体人物行为。

### 可复用代码

- [vlm.py](../../quickcut/vlm.py)：真实关键帧接触表、Ollama 调用、ID 白名单、严格选择校验和推理记录。
- [story.py](../../quickcut/story.py)：故事结构与候选准备的原型；需要区分模型决定与规则修正。
- [plan_summary_acts.py](../../scripts/plan_summary_acts.py)：逐幕调用本地 Qwen、记录纠正过程的已审阅样例。
- [act_config.json](../../examples/chinese_summary/act_config.json)、[editorial_cues.json](../../examples/chinese_summary/editorial_cues.json)：人工约束和人工文案的显式记录方式。

样例中的人工必选镜头和文案不是通用模型能力。迁移时保留其来源标记，不将人工编辑结果记录为未经干预的模型输出。

### P0：首个可联调版本

1. 把 Brief 转成初始段落目的、关键事件、镜头需求和配音风格。
2. 为各段生成 `RetrievalRequest`，区分主内容、环境交代、转场和情绪留白。
3. 根据候选做二次对齐：可支持、部分支持、没有素材支撑的要求分别处理。
4. 调用本地 Qwen 选择实际可见的候选，输出顺序、理由和故事段归属。
5. 生成 StoryPlan，包含确定素材、可替换候选、空镜职责、段落预算和逐句旁白意图。
6. 为每个事实性描述保留对应素材证据；模型错误返回修正请求，不静默替换事件角色。
7. 保存原始响应、校验结果、人工修改和规划版本，支持比较两个故事方案。

### P1：后续增强

同一素材的不同叙事风格、多方案比较、跨文件人物/地点的一致性核对，以及更少人工约束下的完整事件规划。角色对白配音与口型同步属于独立后续能力，不能以普通旁白模块的完成来验收。

### 第一份独立交付

使用一份人工整理的候选集，输出一个完整故事和一个素材不足的案例。先用固定模型响应测试校验器，再接入本地真实推理。C 不必等 B 的排名达到最终效果才开始规划接口。

### 验收与反馈

- 每一段有明确目的，每个选中素材 ID 都出现在候选证据中。
- 外部空镜的位置和作用可解释；故事不能靠重复空镜填满时长。
- 有叙事收束；素材不足时可明确请求补充、改写表达或缩减结构。
- 旁白内容与画面角色、动作和先后关系对照检查；自动格式验证不能替代内容审阅。
- 交给 D 的段落有预算和顺序，交给 E 的句子有 `cue_id`、`beat_id` 和表达要求。

## 6. D：精剪与时间线编排

### 任务的意义

D 把故事板编译成唯一可执行的时间线。粗粒度计划允许“这一段大约六秒”，但渲染和剪映工程需要精确知道每条轨道什么时候开始、什么时候结束。D 负责把模型的意图、素材边界和真实配音时长变成一致的成片安排。

### 范围与输入

输入是 StoryPlan、Manifest 和配音测量结果。D 负责选中片段附近的局部密集采样、出入点细化、动作/对白完整性、同轨冲突、节奏、镜头替换与重排、时间线修订、模块编排和端到端联调。

D 不重新识别整批素材，不自行更改故事事实，也不修改 TTS 音色引擎。镜头长度不足以承接旁白时，D 可以调整时间预算或请求 C 改稿；需要新增素材时向 C/B 发起请求。F 接收的是确定的时间线，不需要自行推断这些决策。

### 可复用代码

- [types.py](../../quickcut/types.py)：现有 Timeline/TimelineItem 的迁移基础，当前 `source_video` 单源结构需要兼容升级。
- [core.py](../../quickcut/core.py)：`validate_timeline`、`update_timeline`。
- [ui.py](../../quickcut/ui.py)：trim、replace、reorder 的交互与校验；现有逻辑不会自动重做完整故事和配音，需补齐失效传播。
- [api.py](../../quickcut/api.py)、[cli.py](../../quickcut/cli.py)：现有调用入口，首版复用，避免另建一套无人维护的演示界面。

### P0：首个可联调版本

1. 维护 EditTimeline 协议与旧 Timeline 的兼容适配，明确版本和源/成片时间转换。
2. 将 StoryPlan 编译成多素材、多轨时间线；每个 clip 都有稳定来源引用。
3. 在候选窗口附近细化入出点，优先保证动作或话语不被意外截断；精细模型未就绪时允许人工确认边界，并记录边界方法。
4. 生成给 E 的初始句子区间或预算，接收实测时长后完成第二次编排。
5. 检查源区间越界、非法同轨重叠、没有说明的空白和超预算。跨轨叠加与明确转场重叠不应误判为错误。
6. 保存时间线修订关系，编辑影响到哪些字幕/配音/渲染片段时，准确标为待更新。
7. 提供最小 orchestration 入口，串联 A/B/C/E/F；失败状态可定位到模块和输入版本。

### P1：后续增强

镜头节奏优化、J-cut/L-cut、动作匹配、音乐节拍约束、细粒度局部重算和交互式候选替换。它们必须进入时间线显式表达，不能只存在于 FFmpeg 的临时命令中，否则剪映无法继续编辑。

### 第一份独立交付

使用手写 StoryPlan 和模拟的配音时长编译一条多源时间线。先验证普通时长，再把其中一句时长加长，确认只有受影响的区间发生可追溯调整。

### 验收与反馈

- 所有片段都有合法来源与源区间；可用数据解释每一帧/每个声音片段的来源。
- 原片帧率、代理帧率和导出帧率不同时，转换结果可验证。
- replace/trim/reorder 后字幕、配音和预览不会继续显示过期状态。
- 若音频无法适配视觉预算，返回明确的重定时或改稿请求，而不是让 F 裁掉末句。
- F 收到的冻结时间线必须精确引用所消费的 VoicePackage 版本；两类文档的 revision 数字无需相等。过期声音包应被拒绝或标记需要重算。

## 7. E：本地配音与字幕

### 任务的意义

E 将故事里的“应该说什么”变成可被剪辑系统使用的真实声音。语音是有实际长度和停顿的媒体，不是用字数推算后就能准确对齐的文本。E 必须交回声音事实，让 D 安排整条片子的时间。

### 范围与输入

输入包括 C 的逐句脚本、D 的预算或视觉区间、语言、音色、语速和表达要求。E 负责本地合成、逐句文件、真实时长、边界静音处理、字幕和声音质量记录。情绪配置要区分“接口允许指定”与“当前引擎确实支持”。

E 不替 C 改变剧情、事实或角色身份，也不自行移动整条画面时间线。外部配音与原声是独立轨道来源；最终原声、旁白和音乐的混合由 F 按 D 的时间线执行。

### 可复用代码

- [voice.py](../../quickcut/voice.py)：`synthesize_local_narration`、逐句 WAV 测量、`synthesize_timed_narration`、SRT、tempo fitting。
- [check_narration_coverage.py](../../scripts/check_narration_coverage.py)：本地 Whisper 旁白末句检查。
- [test_voice.py](../../tests/test_voice.py)、[test_summary.py](../../tests/test_summary.py)：时序与媒体回归基础。

当前中文样例使用 macOS `say` 的 Reed 中文男声和语速参数 145。系统 TTS 的可用音色依赖平台，不应视为跨平台开放模型能力。首轮可以复用该实现，后续本地引擎通过同一适配接口替换。当前函数会回写 Timeline 的字幕与语音信息；新分工应改为显式返回 VoicePackage，由 D 应用更新，避免隐藏的时间线副作用。

### P0：首个可联调版本

1. 封装本地 TTS 引擎接口，明确实际支持的语言、音色和表达参数。
2. 按 `cue_id` 合成一次并保存独立 WAV，记录文本、引擎、配置和真实时长。
3. 剪掉无意义的首尾静音，保留句内表达停顿；支持句末留白。
4. 区分“测量模式”和“指定区间适配模式”。超出可接受的语速调整范围时，返回 `needs_retime`，由 D 调整时间或 C 改稿。
5. 输出与播音文本一致的字幕及句子时间信息；不能把 ASR 猜测文本覆盖成最终字幕。
6. 单句文本或音色变化时可以只重做该句，并明确哪些后续对齐信息已失效。
7. 音频文件与字幕记录引用相同的已批准脚本版本。首次合成依据 StoryPlan revision 返回局部时序，不依赖已存在的 EditTimeline；D 发起指定区间重合成时，再携带并回显该请求的时间线 revision，避免混入旧版本声音或构造循环依赖。

### P1：后续增强

本地神经 TTS 适配、音色试听与选择、多角色一致性、语气更自然的停顿控制和自动发音字典。是否实现某种情绪或声音特征应以实际试听和测量记录验收，不能只依据模型参数名称。

### 第一份独立交付

用三条手写中文句子生成配音：一条短句、一条正常长度句、一条故意超预算的长句。返回 WAV、实际时长、字幕与超时反馈，不等待最终 VLM。

### 验收与反馈

- 每句文本与音频对应，重复运行可追溯，不在切镜头时重复播音。
- 句子与字幕区间合法，实际末词不被截断；无声音与合成失败能够区别。
- 声音参数可复现；返回真实时长而非仅返回字数估计。
- 单句重生成后，D 能识别受影响区间；F 能保留独立配音轨。
- 无法在预算内自然表达的句子明确反馈，不用无限制拉伸或压缩掩盖问题。

## 8. F：渲染与剪映交付

### 任务的意义

F 将内部可编辑时间线交付到用户真正使用的编辑器中，同时产出预览让全组检查。目标是用户接手后还能改镜头、字幕和配音，而不是只能拿到一条已经烧录所有内容的 MP4。

### 范围与输入

输入是冻结版本的 EditTimeline、VoicePackage 和可解析的素材引用。F 负责 FFmpeg 渲染、原声/旁白/音乐混合、预览字幕、素材打包、剪映导出适配、实际打开验证和媒体质量报告。

F 不改变故事内容和全局时间，不能为了让文件导出成功而静默删掉不支持的轨道。目标编辑器不支持的效果需要在导出报告中明确列出，并交给 D/C 决定替代方式。

### 可复用代码

- [core.py](../../quickcut/core.py)：`render_timeline` 的片段渲染、PCM 中间音频与时间戳处理。
- [voice.py](../../quickcut/voice.py)：字幕烧录、原声保留、旁白归一化、混音与峰值限制。
- [verify_chinese_summary.py](../../scripts/verify_chinese_summary.py)：解码、流时长、时间戳、字幕和原声保留的验证基础。

当前仓库尚无已验证的剪映工程导出。其目标版本、工程格式、路径规则和可用功能必须由 F 实机验证，文档不预设存在稳定的通用导入标准。

### P0：首个可联调版本

1. **首先做最小导入实验。** 从一条手写时间线导出两段视频、可编辑字幕和独立配音；记录目标剪映版本和操作系统。
2. 实际打开、修改文字、移动镜头、替换配音、保存和重新打开；确认工程不是只有一个合成视频片段。
3. 建立编辑器能力映射：支持哪些轨道与属性，哪些必须拒绝或显式降级。
4. 将内部时间线映射为目标工程；媒体引用使用可打包、可重定位的机制。
5. 按同一 EditTimeline 渲染预览，保留原声和旁白的独立来源，避免预览与工程出现两套剪辑逻辑。
6. 生成 ExportManifest，记录输入版本、导出目标、文件清单、支持/未支持特性和验证结果。
7. 验证视频可解码、各轨时间一致、声音没有被丢弃、字幕与文字对象可编辑。

### P1：后续增强

增加经过验证的转场、调色、音乐淡入淡出、速度变化和其他轨道属性；每新增一种效果，都分别验证预览结果与工程内编辑结果。跨编辑器适配可以后续增加，内部时间线不应被某个编辑器的私有字段污染。

### 第一份独立交付

F 不等待 A–E 完成。用标准素材和人工时间线做一个最小工程包，先完成实机导入。若格式路线不可行，应立即回报具体版本、失败步骤和功能边界，使架构能尽早调整。

### 验收与反馈

- 指定目标版本能够实际打开、编辑、保存和重新打开工程。
- 主画面、空镜、原声、配音、字幕保留可独立编辑性；字幕不能只存在于烧录画面中。
- 素材包移到新的测试目录后，能完成约定的素材定位或重链接步骤，并记录步骤。
- 预览与工程的顺序、入出点、文字和音频位置一致。
- 全量解码、时间戳与原声保留检查通过；只“生成了 JSON 文件”不算导入成功。
- 失败报告区分媒体损坏、时间线错误、缺失素材、模型产物不完整与目标编辑器不支持。

## 9. 第一轮共同准备：标准样例与接口冻结

在实现真实模型链路之前，六人共同确认一套最小样例。它的目的是给每个模块提供稳定输入，不是假装系统已经能自动生成这些数据。

建议样例包含以下内容：

1. 三段不同长度的用户短视频、一段用户长视频、两段外部空镜；至少覆盖一个无音轨文件和一个不同帧率文件。
2. 一份中文 Brief，明确一个可以由样例素材支撑的三段故事。
3. 手写的 AssetManifest、RetrievalRequest、CandidateSet、StoryPlan。
4. 几句真实可合成的中文配音文本、一份模拟 VoicePackage、一份手写 EditTimeline。
5. 预期行为说明：哪些候选应召回，哪些素材应被排除，哪个音频故意超时，哪些情况下必须返回缺口。

纯协议 JSON 样例不含真实媒体时，只能用于协议校验。媒体验收需要另行提供可播放的素材文件，不能把不存在的示例路径当成真实测试成功。

每个人负责自己输出协议的草稿，D 维护时间与 ID 的共同约定。字段改变必须同时通知消费者，并更新样例与校验器。新增字段优先采用兼容方式；改变单位、语义或必填条件需要明确升级协议版本。

## 10. 里程碑与汇合方式

下表是交付顺序，不是工期承诺。模型效果、硬件环境和剪映适配可行性确认后，再据此估算人日和排期。

| 阶段 | 共同目标 | 通过条件 | 尚不要求 |
|---|---|---|---|
| M0：协议与样例 | 六人能对同一份数据说同一种语言 | 协议字段、ID、时间坐标、示例和失败状态一致；各人能读取自己输入 | 真实模型全部接通 |
| M1：模块独立可运行 | 每个模块都有一个独立入口 | 手写上游输入可运行；有成功和失败案例；F 完成最小剪映实机导入 | 最终检索/叙事效果最优 |
| M2：真实链路串联 | 用真实上游产物替换 mock | 混合长短素材与空镜生成完整工程、独立配音字幕和预览；版本链可追溯 | 复杂特效、多角色口型同步 |
| M3：编辑与异常闭环 | 人工精修不会破坏系统一致性 | 镜头替换/重排、旁白改稿、素材缺失、超时和迁移路径均有正确处理与回归 | 面向所有编辑器版本的兼容 |

每轮只替换一个明确的接口产物。例如 A 的真实 Manifest 替换手写 Manifest 后，B/C/D 的错误可以被定位到字段或素材，而不是一次替换所有模块后一起排查。

模型服务和本地硬件是共享资源。接口测试优先使用固定响应；真实 Qwen/TTS/ASR 运行记录模型与配置。多人共用同一台机器时，约定推理任务排队，避免互相触发内存压力后把超时误认为接口错误。

## 11. 跨模块问题由谁处理

| 现象 | 首要处理人 | 需要协作 | 预期处理 |
|---|---|---|---|
| 关键帧缺失或源时间不对 | A | D | 修复索引或时间映射，标记依赖产物失效 |
| 中文需求找不到相关素材 | B | C | 检查检索表示和约束，返回候选/缺口；C 决定调整结构 |
| 模型颠倒角色或虚构动作 | C | B | 对照证据纠正或重新规划，保留模型原始输出 |
| 旁白超出片段预算 | D | E、C | 先读取真实时长，再调整画面安排或要求改稿 |
| TTS 发音、音色或停顿有问题 | E | C | 调整语音参数或规范化文本，保留原始台词语义 |
| 修改镜头后字幕仍是旧内容 | D | C、E | 触发相关段落和声音的失效/重算 |
| 原声消失、输出时钟不同步 | F | D、E | 对照时间线和独立音轨定位渲染/混音问题 |
| 剪映不能打开或轨道不可编辑 | F | D | 反馈目标版本和能力边界，修复映射或明确拒绝导出 |

## 12. 每次交付的共同要求

每个人交付的不只是代码，还包括接收方可以直接复现的输入输出。所有模块均应提供：

- 输入、输出协议版本及兼容说明。
- 一个可运行入口，区分真实模型模式与 mock/fixture 模式。
- 一组小型示例输入输出，媒体文件用明确引用，不能隐藏在个人目录中。
- 与改动相适应的自动化测试；真实模型结果另存复现命令、模型配置和原始响应。
- 成功、部分成功和失败的处理说明；错误要包含相关项目/素材/段落/句子 ID。
- 已知限制、下一位接收者，以及需要消费者确认的字段变化。

推荐每人使用独立的 `codex/` 前缀分支或团队约定的隔离分支。共享协议和 `types.py`、`core.py` 等多人会触碰的文件，由实际负责的同事集中合并；其他人优先通过适配器调用，避免六条分支同时重写相同核心函数。

### 交付 PR / 交接说明模板

```text
本次交付解决的问题：
负责模块与接收人：

输入：协议名、schema_version、示例路径、需要的媒体
输出：协议名、schema_version、示例路径
运行方式：安装前提、命令、真实模型或 mock 标记

已验证：
- 成功案例及结果
- 失败/缺口案例及结果
- 对时间、素材来源和依赖版本的检查

接口变化：新增/修改字段及消费者影响
已知限制：尚未支持的场景，不用成功样例掩盖
接收方下一步：应该运行哪条命令，检查哪些字段或媒体
```

## 13. 整体完成标准

第一阶段的共同验收输入，是一组长短视频、外部空镜库与一个用户故事要求。输出应是一条不超过已约定时长预算的完整故事：主内容有来源、空镜有作用、旁白与画面对应、原声被保留，且能在已记录的剪映目标版本中独立修改镜头、字幕和配音。

完成标准包含一次真实的人工精修：打开工程、替换一个镜头、修改一句字幕或配音、保存后重新打开并导出。这样才能确认六位同事的交付真正连接到用户的工作方式，而不止连接到一个演示 MP4。
